## O que é o projeto

SIGES (Siges Serviços Financeiros) é um SaaS de gestão de empréstimos, construído inteiramente por conversa com o Claude Code. Dois papéis: **cliente** (autocadastro, acesso restrito ao próprio contrato) e **gerente/administrador** (acesso total, só é criado internamente por outro gerente — nunca há tela pública de cadastro de gerente). Na UI o papel `gerente` é chamado de "Administrador" — a nomenclatura interna do código (roles, `is_gerente()`, nomes de tabela) continua "gerente" de propósito; não vale a pena renomear (risco alto, zero ganho pro usuário).

Stack: HTML/CSS/JS vanilla sem build/bundler, Supabase (Postgres + Auth + Realtime), Vercel (hospedagem estática + serverless `/api`), GitHub (código-fonte). Detalhes de arquitetura e passo a passo de deploy: [README.md](README.md).

## Como o usuário trabalha comigo

- O usuário manda listas numeradas de melhorias ("Melhorias a fazer no sistema") em rodadas grandes. Implemento tudo que for possível diretamente; itens que pedem uma decisão de negócio (ex: mudar uma fórmula de cálculo) devem ser **analisados e propostos primeiro**, nunca implementados sem aprovação explícita — ele é claro quando quer isso ("estude bem, analise bem... me traga sugestões").
- **Nunca faço `git push` sem confirmação explícita** ("pode enviar", "sim, pode mandar" etc.) — mesmo depois de implementar e testar tudo.
- Quando uma mudança exige rodar uma migration no Supabase, **o usuário roda manualmente** no SQL Editor (não tenho acesso direto ao banco de produção). Só confio que uma função/coluna nova existe em produção depois que ele confirma que rodou a migration.
- Regra especial já usada: se o usuário pedir para eu não interromper o fluxo para pedir aprovações intermediárias, devo implementar tudo primeiro e deixar **uma lista consolidada única** de ações pendentes dele (migrations a rodar, confirmação de push) para o final.
- Sempre testo mudanças de UI no preview antes de reportar como concluído (ver seção de gotchas abaixo sobre cache).
- **Toda vez que um arquivo em `api/*.js` for criado, removido, renomeado, ou tiver a assinatura de `req`/`res` alterada, atualize também o pacote de migração em `netlify/` no mesmo commit** (ver seção "Pacote de migração para Netlify" abaixo) — ele existe pra ficar pronto pra ativar a qualquer momento, e um pacote desatualizado é pior que não ter pacote nenhum (falha silenciosa na hora que mais importa). Mudança de LÓGICA INTERNA de um handler (sem mexer em `req`/`res`/nome do arquivo) não exige tocar em `netlify/` — o wrapper só reexporta o handler original, então já acompanha sozinho.

## Estado das migrations (verifique isto sempre)

`supabase/schema.sql` é a fonte da verdade "fresh install" (sempre mantida em sincronia com a última migration). As migrations em `supabase/migration_00N.sql` são incrementais e devem ser rodadas em ordem crescente, uma vez cada, no SQL Editor do Supabase em produção.

Rode `git status` em `supabase/` para ver quais migrations ainda não foram commitadas (== ainda não confirmadas como rodadas pelo usuário). Migrations não commitadas normalmente significam "ainda não rodei isso em produção" — **nunca assuma que uma coluna/função de uma migration recente já existe em produção sem confirmar com o usuário.**

## Decisões de arquitetura não óbvias (o "porquê")

- **FKs de `notifications_log`, `renewal_cycles`↔`installments`, `payments`, `loan_requests.resulting_contract_id` são todas `ON DELETE SET NULL` ou `CASCADE`** — corrigido depois de um bug recorrente de violação de FK ao excluir contrato/parcela. Havia uma referência circular entre `installments.renewed_into_cycle_id` e `renewal_cycles.origin_installment_id` que tornava impossível qualquer ordem de DELETE funcionar sem esse fix no schema. Se um bug de FK "voltar", o problema quase certamente é uma FK nova que falta esse tratamento — não é reordenar DELETEs em `delete_contract()`.
- **`late_fee_percent`/`late_interest_percent`** (contrato) são aplicados **no momento do recebimento** (quitação OU renovação de parcela/ciclo atrasado), não acumulados automaticamente por um cron. Cálculo: juros de atraso = `saldo_da_parcela × ((1 + late_interest_percent/100)^dias_atraso − 1)` — **juros compostos, taxa DIÁRIA** (decisão explícita do usuário em 2026-07-08, revendo a versão anterior que era simples/mensal — confirmado com exemplo numérico: 1300 a 2%/dia por 8 dias = 1523,16). Multa = `saldo × late_fee_percent/100` (fixa, não escala com dias, sem juros compostos). Ambos os valores aparecem como sugestão editável no modal de recebimento (`gerente-contrato-receber.js`) — o gerente pode ajustar/zerar, tanto na aba "Quitar" quanto na "Renovar". O valor cobrado além do saldo contratual da parcela vira `payments.late_charge_amount`, somado a `interest_component` (assim relatórios/lucro líquido já enxergam automaticamente, sem precisar tocar em cada consumidor). O rótulo do campo é "% ao dia", não "% a.m." — contratos antigos que preencheram esse campo pensando em taxa mensal vão ter o valor reinterpretado como diário (crescimento bem mais agressivo); se isso for um problema, contratos existentes precisam ter `late_interest_percent` ajustado manualmente pelo admin.
- **`refresh_overdue_status()`** (cron diário) recalcula o score de todo cliente com contrato `atrasado`/`perda` a cada execução — sem isso, o score de um cliente inadimplente que não interage mais com o sistema ficaria parado no valor antigo.
- **`payments.net_profit`** é uma coluna gerada (`interest_component - operational_fee_amount`) — é a base de "lucro líquido" em todo o sistema (relatórios, resumo do contrato). Encargo de atraso já está embutido em `interest_component`, então flui automaticamente.
- **Taxa de saída** (`loan_contracts.operational_fee_amount`) é cobrada **uma vez**, na criação do contrato, e soma ao "Total desembolsado" (`total_disbursed_amount`, coluna gerada = `principal_amount + operational_fee_amount`). **Taxa de entrada** (`payments.operational_fee_amount`) é cobrada a cada recebimento. Lucro líquido do contrato = juros recebidos (parcelas + renovações) − taxa de saída (uma vez) − soma das taxas de entrada — já implementado no card "Resumo do contrato" em `gerente-contratos-lista.js` (tela de detalhe).
- **Renovação (`renew_installment`) só é permitida em contratos de parcela única** (`installments_count === 1`) — renovar uma única parcela de um contrato multi-parcela deixaria a relação entre as outras parcelas e o ciclo renovado ambígua.
- **CPF no login**: `doSignIn` detecta se o texto digitado parece CPF (11 dígitos, sem `@`) e resolve para e-mail via RPC `email_for_cpf` antes de chamar `signInWithPassword`.
- **`clients.salary` é `text`, não `numeric`** (mudou na migration_008) — guarda uma das 4 faixas fixas de `INCOME_BRACKETS` (`js/utils.js`), rotulado "Renda Mensal" na UI. Não é usado em nenhum cálculo automático, é só informativo. Clientes cadastrados antes da migration_008 têm o valor numérico antigo salvo como texto (ex: `"3245.00"`) — não bate com nenhuma das 4 opções, então o `<select>` mostra em branco até o admin escolher uma faixa manualmente. Para adicionar/mudar faixas, edite só `INCOME_BRACKETS` em `js/utils.js` — os dois formulários (`login.js` cadastro e `gerente-clientes.js` edição) consomem a mesma constante via `incomeBracketOptionsHtml()`.
- **Inputs `type="number"`/`type="date"`**: `style.css` já remove o spinner nativo e estiliza o ícone do calendário para não destoar do resto do design flat/minimalista — não reintroduza esses controles nativos sem essa camada de CSS.
- **`clients` NÃO tem colunas `cpf`/`phone`** — essas ficam só em `profiles`. Um bug antigo (corrigido na migration_010) tinha `handle_new_user()` tentando inserir `cpf`/`phone` em `clients`, quebrando **todo** cadastro público de cliente com "Database error saving new user" (erro Postgres 42703). Se qualquer função nova mexer em dados de cliente, sempre confira contra o `create table clients (...)` real no `schema.sql` antes de assumir quais colunas existem lá — não pelo nome do campo no formulário.
- **`system_settings` exige `auth.uid() is not null` para SELECT** (corrigido na migration_010) — antes qualquer visitante não-autenticado conseguia ler taxas internas/thresholds direto pela API REST do Supabase (a anon key é pública). Se precisar expor mais uma tabela de configuração, nunca use `using (true)` sem pensar se aquilo devia ser público. (A "Tabela VIP", `loan_rate_reference`, existia com essa mesma proteção mas foi **removida por completo** na migration_013 — era só uma sugestão visual morta, nunca travava nada.)
- **Limite de crédito consome CAPITAL emprestado (`client_outstanding_principal()`), não o saldo devedor total.** `client_outstanding_balance()` (saldo com juros) existe só para exibir dívida ao cliente ("quanto falta pagar") — nunca para calcular/checar limite disponível. Não confundir os dois em código novo: limite de crédito = quanto capital ainda está emprestado; saldo devedor = quanto falta pagar (capital+juros). Bug real já causado por essa confusão: `cliente-dashboard.js` (card "Limite disponível" do Início) usava por engano `client_outstanding_balance`, divergindo do valor correto mostrado em `cliente-solicitar.js` (que sempre usou `client_outstanding_principal`) — corrigido em 2026-07-10. Qualquer tela nova que mostre "limite disponível" deve usar `client_outstanding_principal`.
- **Status "atrasada" de parcela/ciclo tem até 24h de atraso em relação à realidade**, porque só é setado pelo cron diário `refresh_overdue_status()`. Por isso, `gerente-cobrar.js`, `gerente-dashboard.js` e os badges de status (`effectiveInstallmentStatus()` em `js/utils.js`) NUNCA filtram/exibem status de atraso comparando só a coluna `status` — sempre comparam `due_date < hoje` ao vivo. Se adicionar uma tela nova que lista parcelas atrasadas, replique esse padrão (não confie só em `status = 'atrasada'`).
- **`clients` não tem mais `region`** (removida — só existe `client_group`, que agora é uma lista fixa de 5 valores em `CLIENT_GROUPS`, `js/utils.js`). Client group é capturado tanto no cadastro público (`login.js`) quanto na edição pelo admin (`gerente-clientes.js`).
- **Backup/exportação** (`js/screens/backup-export.js`): backup automático roda no máximo 1x por período configurado (`system_settings.backup_frequency`), verificado via `localStorage` (por navegador/dispositivo, não por conta) logo após login do gerente (`maybeRunAutoBackup()` em `onAuthenticated`). Exportação usa SheetJS (XLSX, via CDN) e jsPDF (PDF no estilo do extrato) — nenhuma delas grava nada no servidor, é tudo download direto no navegador.
- **"Planejamento"** (`js/screens/gerente-planejamento.js`, tabela `planning_debts`) é um retrato único ("se eu parasse de emprestar hoje, quanto sobra"), não uma projeção mês a mês — por isso taxa de saída/entrada são aplicadas **uma vez sobre o valor agregado** (Dívida base somada, Faturamento base somado), não parcela a parcela. Dívida base = soma manual de `planning_debts.amount` (dívidas nomeadas, uma data `month` cada, sem limite real de uso — a UI só oferece os próximos 12 meses no seletor). Faturamento base = `system_settings.planning_current_cash` (caixa atual, editado manualmente na própria tela) + soma de **todas** as parcelas/ciclos `pendente`/`atrasada` em aberto no sistema inteiro (sem corte de data — é "tudo que ainda vou receber"). LTV (`system_settings.planning_ltv_percent`) é editado manualmente na mesma tela e desconta do Lucro Bruto pra chegar no Lucro Líquido. Isso é **diferente** do gráfico "Projeção de Lucro (6 meses)" do dashboard (`gerente-dashboard.js`), que É uma projeção mês a mês e aplica a taxa de entrada **por parcela/ciclo individual** (já que ali cada mês soma transações discretas) — não confundir os dois modelos de cálculo ao mexer em qualquer um dos dois.
- **Gráficos de projeção (`areaChartSVG`, `js/charts.js`)**: o rótulo de valor de cada ponto é **sempre desenhado acima do ponto** e em cor fixa (`--ink`, com halo branco atrás via `paint-order:stroke`), nunca na mesma cor da linha/área — o usuário reportou um valor ilegível quando caía em cima de uma linha da mesma cor. Se criar um gráfico de projeção novo, reuse `areaChartSVG` em vez de reinventar rotulagem.
- **Score de crédito (`recalculate_client_score()`)**: fórmula revisada em 2026-07-10/11 (aprovada pelo usuário, com ajustes dele em várias rodadas). **Sistema de "graduação"**: todo cliente novo começa e **permanece com score-base 50** até quitar o primeiro contrato OU pagar a primeira renovação — só nesse marco ("graduado") os BÔNUS de comportamento passam a valer, com piso recentralizado em **70**. **Pós-graduação (2026-07-10, regra mais rígida)**: o bônus (até **+30 pts**) não é mais soma direta de percentuais — é o PRODUTO de `qualidade` (0–1, consistência de pagamento: em dia/adiantado) × `maturidade` (0–1, volume de histórico acumulado — parcelas pagas + contratos quitados + renovações em dia — via `1 - e^(-volume/8)`, retornos decrescentes). Isso torna cada ponto progressivamente mais caro: 1-2 contratos bons chegam a ~80, mas 90-100 exige dezenas de eventos positivos sustentados — impossível de forçar rápido só fazendo contratos em sequência (bug real corrigido: 1 contrato quitado adiantado batia ~100 antes dessa mudança). **Mas as penalidades de risco valem SEMPRE, graduado ou não**: atraso médio histórico (até −20 pts, `v_delay_penalty`), atraso ATUAL — parcela/ciclo vencido e ainda não pago, mesmo padrão "due_date < hoje ao vivo" do resto do sistema (−15 pts fixos, `v_overdue_penalty`), e qualquer contrato em `perda` (−30 pts fixos, `v_perda_penalty`). **Reprovação de solicitação de empréstimo NÃO é critério** (removida por completo — decisão explícita do usuário: "isso jamais deve ser critério de avaliação"). Faixas de tier: Ouro ≥85, Bom 70–84, Atenção 50–69, Alto risco <50 (o limiar 70 é o MESMO usado pra separar as duas listas da tela — ver abaixo). A regra completa NÃO fica mais fixa na tela (poluía o visual) — vive num modal (`openScoreHelpModal()` em `gerente-score.js`), aberto pelo ícone "?" injetado ao lado do título na topbar via `injectScoreHelpButton()` (funciona porque o router seta `topbar-title` ANTES de chamar `render()` — o render pode sobrescrever o innerHTML com o botão, e o próximo `router.handleHashChange()` limpa isso de novo via `textContent =`). Se mudar a fórmula no SQL, atualize esse modal também, senão ficam dessincronizados.
- **Listas "Ranking — melhores scores" / "Atenção — menores scores"** (`gerente-score.js`): são uma **partição estrita por limiar** (`score >= 70` → melhores, `< 70` → piores), nunca mais um "top 10 / bottom 10" por slice — o slice antigo causava um cliente aparecer nas duas listas ao mesmo tempo sempre que havia poucos clientes no total. Se mudar o limiar de graduação (hoje 70), replique a mudança aqui.
- **Dashboard — comparação temporal**: os deltas "▲/▼ X% vs. mês passado" (card de destaque de lucro líquido e "Recebido no mês") comparam o mês corrente **até hoje** com o **mesmo intervalo de dias do mês anterior** (não o mês anterior inteiro) — comparar parcial vs. completo seria injusto (mês em andamento sempre perderia). Lógica em `trendBadgeHtml()` e no cálculo de `prevMonthStart`/`prevMonthEnd` no topo de `renderGerenteDashboard()`.
- **"Top clientes por saldo em aberto"** (dashboard): não usa nenhuma RPC nova — reaproveita as mesmas queries de `installments`/`renewal_cycles` pendentes/atrasados já usadas na projeção de recebimentos, só que com o relacionamento (`loan_contracts!...(client_id, clients!...(profiles!...(full_name)))`) embutido no `select()` pra trazer o nome do cliente junto, e agrupa/soma no JS. Mesmo padrão de embed usado em `gerente-cobrar.js`.
- **`payments.received_at` e `installments.paid_at` são `timestamptz`, mas todas as RPCs de recebimento só gravam uma DATA** (`coalesce(p_received_at, current_date)`, sem hora real) — o Postgres casteia isso pra meia-noite UTC. Formatar com `formatDateTime()` (que usa fuso LOCAL do navegador) desloca pro dia anterior em qualquer fuso negativo (ex: Manaus UTC-4 → 00:00 UTC vira 20:00 do dia anterior). Use sempre `formatDateUTC()` (`js/utils.js`) pra esses dois campos — ela força `timeZone: 'UTC'` no `toLocaleDateString`, recuperando a data exata que foi selecionada. Se adicionar uma tela nova que mostra `received_at`/`paid_at`, replique esse padrão (não use `formatDateTime`/`formatDate` direto neles).
- **Barra de busca perdendo foco a cada tecla**: telas que fazem `root.innerHTML = ...` inteiro dentro do próprio handler de busca (debounced) recriam o `<input>` do zero a cada repaint, matando o foco/cursor. Padrão de correção usado em `gerente-clientes.js` e `gerente-contratos-lista.js`: no início da função de render, capturar `document.activeElement === inputAntigo` e `selectionStart`; depois de montar o novo HTML, se tinha foco, chamar `.focus()` + `.setSelectionRange()` no novo input. `gerente-contrato-novo.js` não sofre disso porque seu `paintClientList()` só substitui a `<div>` da lista, nunca o `<input>` de busca em si — esse é o padrão preferível pra buscas novas (isolar o repaint da lista do repaint do input).
- **Importação em massa de clientes de sistema antigo** (feita uma vez em 2026-07-11, 35 clientes via PDFs do sistema anterior): a técnica foi inserir direto em `auth.users` com senha via `crypt(senha, gen_salt('bf'))` (extensão `pgcrypto`) dentro de um `do $$ ... end $$` por cliente, deixando o trigger `handle_new_user()` já existente criar `profiles`/`clients` a partir do `raw_user_meta_data`. Clientes sem e-mail no sistema antigo receberam um e-mail placeholder (`<cpf-digitos>@sememail.siges.app`) só pra existir uma linha válida em `auth.users` — o login deles continua funcionando normalmente por CPF (via `email_for_cpf`), o placeholder nunca aparece pra eles. Script consumido uma única vez, não faz parte do histórico de migrations numeradas (é dado, não schema) — se precisar importar mais gente no futuro, reusar esse mesmo padrão.
- **Texto de cobrança via WhatsApp** (`buildWhatsappUrl()` em `gerente-cobrar.js`) inclui uma estimativa de juros de atraso + multa (mesma fórmula composta diária do modal de recebimento) quando a parcela/ciclo já está vencido — é só uma SUGESTÃO no texto, o valor final cobrado continua sendo o que o gerente ajustar na hora de receber de verdade.
- **PDF de "Exportar dados"** (`runExportPDF()` em `backup-export.js`) é organizado por CLIENTE (nome → contratos → parcelas em aberto de cada contrato), não mais em 4 tabelas soltas sem relação entre si. A seção "Pagamentos" no fim continua como lista flat separada (histórico, não "em aberto") — se pedirem pra também agrupar pagamentos por cliente, é uma extensão do mesmo padrão (`contractsByClient`/`openInstallmentsByContract` já prontos pra reusar a lógica).
- **Menu mobile "Mais"** (`#mobile-more-menu` + `#mobile-more-backdrop` em `index.html`, lógica em `main.js`): a tabbar mobile só cabe ~5 itens legíveis, mas o gerente tem 10 rotas no menu. `MOBILE_TAB_ROUTES.gerente` define só as 4 mais usadas como aba direta (Dashboard/Cobrar/Contratos/Relatórios); o resto vira uma folha (`toggleMobileMoreMenu()`) que abre por cima da tabbar com grid 3 colunas. Fecha automaticamente ao navegar (via `closeMobileMoreMenu()`, já chamado em todo `router.handleHashChange()`) ou ao clicar no backdrop. Cliente só tem 5 rotas então cabe inteiro sem "Mais".
- **Hash da URL preso entre sessões**: `doSignIn`/`doSignUp`/`handleSignOut` agora fazem `location.hash = ''` antes de autenticar/deslogar — sem isso, se o usuário saía estando em `#/cliente/emprestimos`, o hash ficava na URL e o próximo login caía direto naquela tela em vez do Dashboard (`onAuthenticated()` só força Dashboard quando o hash já está vazio). Qualquer novo fluxo de auth (ex: um terceiro provedor OAuth) precisa do mesmo cuidado.
- **Transferência de score do sistema antigo** (feita uma vez, 2026-07-11): é só um valor inicial "cosmético" — a regra de graduação do Siges recalcula o score de qualquer cliente no primeiro evento real dele (pagamento, quitação, ou um clique em "Recalcular todos"), e como os clientes importados começam sem nenhum histórico de pagamento NO SIGES, esse recálculo os leva de volta a 50 (não graduados). Não é uma transferência permanente de histórico de crédito, só evita começar todo mundo igual visualmente no dia da importação.
- **Senha do cliente (e agora do gerente) NÃO é visível pro admin, nem pode ser** — Supabase Auth guarda senha como hash bcrypt irreversível, não existe "ver a senha atual/trocada pelo usuário". Em vez disso, o admin **redefine** a senha em `gerente-clientes.js`/`gerente-gerentes.js` (seção "Redefinir senha" dentro do modal de editar, só no modo edição) → `POST /api/reset-client-password` (mesmo endpoint serve os dois casos, apesar do nome — service_role, `PUT /auth/v1/admin/users/{id}` com `{password}}`) → nova senha fica visível só no campo que o próprio admin acabou de digitar (repassa manualmente). `/api/reset-client-password.js` e `/api/update-user-email.js` (2026-07-11) agora checam o papel do ALVO via `getTargetProfile()` (`api/_lib/supabaseAdmin.js`): se o alvo é `role='gerente'`, exige `caller.is_primary_admin` — senão um gerente secundário conseguiria resetar a senha/e-mail de outro administrador (inclusive o primário) e sequestrar a conta. Clientes continuam abertos pra qualquer gerente ativo mexer.
- **Trilha de auditoria** (`audit_log` + RPC `log_audit_event(p_action, p_description, p_metadata)`, tela `gerente-auditoria.js`, entre Planejamento e Configurações no menu): callable por `anon` E `authenticated` de propósito — precisa registrar `login_falho`/`login_sucesso` mesmo SEM sessão totalmente estabelecida (usa `auth.uid()`, que é `null` no caso de falha; `actor_name`/`actor_role` viram "Anônimo"/`null`). RLS só permite SELECT pra `is_gerente()`; não existe policy de INSERT — a função é `security definer` e roda como dono da tabela, bypassa RLS (mesmo padrão de toda função `security definer` do schema). Helper JS `logAudit(action, description, metadata)` em `state.js`, chamado após sucesso em: criar/editar/excluir cliente, aprovar/rejeitar cadastro, redefinir senha, criar/editar/excluir contrato, editar parcela, receber pagamento, renovar, criar/editar gerente, e login com/sem sucesso. **Login bem-sucedido** é capturado no listener `supa.auth.onAuthStateChange` de `auth.js`, filtrando especificamente `event === 'SIGNED_IN'` (dispara só em login de verdade — senha ou Google) e nunca em `'INITIAL_SESSION'` (restauração de sessão ao recarregar a página) — não confundir os dois eventos se mexer nesse listener. Erros JS não tratados viram `erro_sistema` automaticamente via `window.onerror`/`unhandledrejection` em `main.js` — **não** cobre todo `try/catch` manualmente (seria um projeto à parte); se quiser mais eventos cobertos, é instrumentar caso a caso com `logAudit(...)`.
- **Papéis "Administrador" (admin primário) vs "Gerente" (secundário)** (2026-07-11, decisão explícita do usuário): na UI, `is_primary_admin=true` agora é rotulado **"Administrador"** (antes "Admin primário") e `is_primary_admin=false` é **"Gerente"** (antes também aparecia como "Administrador" — os dois papéis eram indistinguíveis pro usuário final). ## Cuidado com `create or replace function` e parâmetros

**`CREATE OR REPLACE FUNCTION` só substitui a função existente se o nome E os TIPOS dos parâmetros forem idênticos aos já cadastrados.** Se você mudar o TIPO de um parâmetro existente (ex: `p_salary numeric` → `p_salary text`) ou mudar a ARIDADE (adicionar/remover parâmetro), o Postgres cria uma **segunda função sobrecarregada (overload)** em vez de substituir — as duas ficam coexistindo no banco.

Isso já causou um bug real (migration_008 mudou `update_client_profile`'s `p_salary` de `numeric` para `text`, sem trocar nome/quantidade de parâmetros — resultado: duas versões idênticas em nome e nomes-de-parâmetro, e o PostgREST não conseguia mais decidir qual usar, dando "Could not choose the best candidate function" em todo salvamento de cliente pelo admin). Corrigido na migration_010 com `drop function if exists <nome>(<tipos antigos exatos>);` antes do `create or replace`.

**Regra prática:** toda vez que uma migration mudar o TIPO de um parâmetro existente ou adicionar/remover parâmetro de uma função já em produção, inclua um `drop function if exists nome(tipos-antigos-exatos-na-ordem);` ANTES do `create or replace function`, pegando os tipos antigos exatos do `git show <commit-anterior>:supabase/schema.sql`.

## Gotchas de teste/verificação

- **Service Worker cacheia agressivamente.** Se algo que você editou parece "não ter efeito" no preview, ou o browser mostra uma versão antiga do JS mesmo após reload, rode isto no console/`preview_eval` antes de qualquer outra investigação:
  ```js
  (async () => {
    const regs = await navigator.serviceWorker.getRegistrations();
    for (const r of regs) await r.unregister();
    const keys = await caches.keys();
    for (const k of keys) await caches.delete(k);
    location.reload();
  })();
  ```
  Isso já causou pelo menos um "bug" reportado pelo usuário que na verdade era cache — sempre descarte essa hipótese antes de mexer em código que já parece correto na leitura.
- **Sempre suba `CACHE_NAME` em `sw.js`** ao final de uma rodada com mudanças relevantes de JS/CSS (está em `v15` agora) — isso força o Service Worker do usuário em produção a invalidar o cache antigo no próximo load.
- Para testar telas de gerente no preview sem depender de dados reais do Supabase (RLS bloqueia sessão fake), mocke `supa.from` com um proxy "chainable" que resolve para dados fake, teste, e restaure `supa.from` original antes de terminar. Às vezes só desregistrar o Service Worker + limpar caches não basta pro `preview_eval` pegar o JS novo (o servidor estático do preview também cacheia o `<script src>` de cada arquivo individualmente, mesmo depois de um hard navigate com cache-bust na URL da página) — se uma variável/função continuar "antiga" depois do procedimento padrão, faça `fetch(caminho, {cache:'no-store'}).then(r=>r.text())` e `(0, eval)(texto)` pra aplicar o conteúdo atual na sessão do browser. **Atualização (2026-07-11): às vezes até `{cache:'no-store'}` sozinho continua servindo conteúdo velho** — só resolve de fato acrescentando um cache-buster na URL do fetch (`fetch(caminho + '?v=' + Date.now(), {cache:'no-store'})`). Se mesmo assim uma função global (ex: `router.handleHashChange`) continuar com o código antigo (teste rápido: `algumaFuncao.toString().includes('trechoNovo')`), o hard-navigate comum não bastou — chame `navigate` com `{force:true}` pra forçar um reload de verdade da página inteira.
- **`(0, eval)` não funciona em arquivos com `const`/`let` no escopo top-level que já rodaram uma vez na página** (ex: `js/main.js`, que declara `const NAV_ITEMS`/`const MOBILE_TAB_ROUTES`; `js/router.js`, que declara `const ROUTES`/`const router`) — reavaliar o texto do arquivo gera `SyntaxError: Identifier ... has already been declared`, que aborta o `eval` inteiro em silêncio (a Promise só rejeita, nada aparece no retorno se você não tratar o erro) e as variáveis global continuam com o valor antigo. Pra esses arquivos específicos, rode o texto dentro de `new Function(texto + '; suaFuncaoDeRender();')()` — isso executa num escopo de função isolado (sem colidir com os `const` já existentes no global) e ainda deixa você chamar a função de render logo em seguida pra inspecionar o DOM resultante. **Isso NÃO serve pra "hot-patchar" um singleton como `router`** — o `router`/`ROUTES` recriados dentro do `new Function` isolado ficam desconectados do `router` global que o resto do app já referencia (closures antigas de `hashchange` continuam presas na versão velha); pra esses dois arquivos específicos, é mais simples forçar reload completo (`navigate` com `force:true`) do que tentar hot-patch. Arquivos de tela normais (`js/screens/*.js`) só usam `function` no top-level, que PODE ser redeclarada sem erro — `(0, eval)` funciona neles direto.

## Auditoria de pagamento parcial (2026-07-12, `migration_022`)

Rodada de testes dirigidos a cenários de recebimento parcial de parcela — 8 cenários rastreados manualmente (linha a linha do SQL), 2 bugs reais encontrados e corrigidos nesta migration, 2 achados baixos também corrigidos:

- **`receive_cycle_payment()` (quitar um ciclo de renovação) não validava o valor recebido contra o devido** — diferente de `receive_payment()` (parcela normal), que já bloqueia valores fora do permitido tanto no JS quanto no SQL. Um valor MENOR que o `full_debt_amount` do ciclo era aceito do mesmo jeito, o ciclo (e o contrato, se fosse a última pendência) era marcado como quitado, e os componentes gravados em `payments` (`principal_component`/`interest_component`) eram o valor CHEIO esperado, não o que realmente veio em `p_amount_received` — ou seja, o sistema registrava lucro que não entrou de verdade. **Ciclo de renovação não tem colunas de controle de pagamento parcial** (diferente de `installments`, que tem `principal_paid_partial`/`interest_paid_partial`) — a correção escolhida (das duas possíveis) foi exigir que o valor recebido seja igual ao valor cheio devido (`full_debt_amount + encargo de atraso`, tolerância de 1 centavo), rejeitando qualquer coisa fora disso com `INVALID_AMOUNT`. Reforçado também no JS (`gerente-contrato-receber.js`) com uma mensagem amigável explicando que ciclos não suportam parcial e sugerindo usar "Renovar" se o cliente só puder pagar uma parte.
- **`renew_installment()`, ao renovar direto de uma PARCELA, ignorava pagamento parcial já recebido** — lia `principal_share`/`interest_share` brutos (os valores originais do contrato) em vez de descontar `principal_paid_partial`/`interest_paid_partial` já pagos. Se uma parcela recebia pagamento parcial e depois era renovada (em vez de continuar sendo quitada), o valor já pago "sumia": o novo ciclo nascia cobrando a dívida CHEIA original, inflando o saldo devedor do cliente exatamente pelo valor que ele já tinha pago. Corrigido subtraindo `principal_paid_partial`/`interest_paid_partial` no `select` que lê a parcela (mesmo ajuste que `receive_payment` já fazia corretamente), com `greatest(0, ...)` como defesa extra contra qualquer estado inconsistente anterior. O branch que renova a partir de um CICLO já existente (não de uma parcela) não tinha esse problema — `renewal_cycles` não tem coluna de pagamento parcial, então `full_debt_amount` já representa o saldo remanescente real.
- **`update_installment_schedule()` (editar/reagendar parcela) não validava contra o que já foi pago** — deixava reduzir `principal_share`/`interest_share` pra um valor abaixo de `principal_paid_partial`/`interest_paid_partial` já registrados, o que geraria saldo restante negativo (`amount_due - paid_partial < 0`) e um "Pago parcial: resta R$-X" confuso nas telas do cliente. Agora rejeita com `AMOUNT_BELOW_ALREADY_PAID` (mapeado pra mensagem amigável no modal), e o próprio modal mostra um aviso em vermelho com o valor já pago quando a parcela editada já tem pagamento parcial.
- **Confirmado correto e não alterado**: alocação juros-primeiro-depois-capital em pagamento parcial de parcela normal; acúmulo correto de múltiplos pagamentos parciais na mesma parcela; `client_outstanding_balance()`/`client_outstanding_principal()` já descontavam pagamento parcial de parcela normal; bloqueio de valor inválido (zero/negativo/acima do permitido) em `receive_payment`; proteção contra corrida (`for update` + recheck de status) em todas as funções de recebimento; parcela parcialmente paga nunca conta como "paga" no score (comportamento intencional).

## Bug real corrigido: exibição de ciclos renovados nas telas do cliente (2026-07-12, `migration_023`)

Reportado pelo usuário com print real: contrato de parcela única renovado 3x mostrava as linhas intermediárias ("Renovação 1"/"Renovação 2") com um traço no lugar do badge de status, e o valor de TODAS as linhas de renovação mostrava a dívida cheia (ex: R$650) em vez do que foi de fato pago naquela renovação (só juros, ex: R$150).

- **Causa raiz**: `cliente-emprestimos.js`/`cliente-indicacoes.js` tinham dois problemas no `cyc.map(...)` que renderiza a tabela de parcelas/ciclos: (1) o mapa de labels de status (`{ pendente: 'Pendente', paga: 'Paga', atrasada: 'Atrasada' }`) não incluía `renovada` — resultado `undefined`, badge vazio (o traço visto no print); (2) a coluna "Valor" sempre mostrava `r.full_debt_amount` (a dívida CHEIA que rola pro próximo ciclo), nunca `r.interest_only_amount` (o que foi realmente pago NESSA renovação — só juros). **A tela de admin (`gerente-contratos-lista.js`, card "Ciclos de renovação") nunca teve esse bug** — já mostra as duas colunas separadas ("Juros pago" = `interest_only_amount`, "Dívida renovada" = `full_debt_amount`) e já tinha `renovada` no mapa de status; o bug era exclusivo das 2 telas do cliente.
- **Correção**: `renovada` adicionado ao mapa de status nas duas telas. Valor da linha agora é condicional: `status === 'renovada'` → mostra `interest_only_amount` (o juros pago nessa renovação específica); qualquer outro status (`pendente`/`atrasada`/`paga`) → mostra `full_debt_amount` como antes (pra um ciclo ainda aberto, isso é corretamente "quanto falta pagar"; pra um ciclo `paga`, é corretamente "quanto foi pago na quitação final", já que `receive_cycle_payment` só aceita o valor cheio — ver achado anterior).
- **Melhoria de nomenclatura pedida junto**: a última linha de um contrato renovado (status `paga`, quitação final) mostrava "Renovação N" como as outras — agora mostra **"Quitação"**, já que semanticamente não é mais uma renovação, é o encerramento da dívida.

## Análise de continuidade: formato de backup e portabilidade de hospedagem (2026-07-13)

Pedido do usuário: analisar (sem implementar ainda) os dois riscos mais sérios já levantados numa auditoria anterior — perda de dados e disponibilidade da Vercel. Entregue como artifact único (favicon 🧭, "análise inicial") cobrindo os dois temas. Nenhuma mudança de código nesta rodada — só análise + recomendação, seguindo a convenção do projeto de propor antes de implementar decisões arquiteturais.

- **Backup (.json)**: confirmado por leitura de `collectAllSystemData()` (`js/screens/backup-export.js`) que o backup diário cobre 6 tabelas (clientes/contratos/parcelas/ciclos/pagamentos/solicitações) mas **não** inclui `system_settings`, `planning_debts`, `audit_log`, `notifications_log`, `push_subscriptions` nem perfis de gerente. **Não existe nenhuma função de importação/restauração em lugar nenhum do código** — o app só exporta. Resposta direta à pergunta do usuário ("consigo restaurar com o .json?"): hoje, não, sem escrever um script novo na hora. Isso não é um problema do formato JSON em si (ele preserva os dados perfeitamente) — é a ausência de um caminho de restauração pronto. Senha de login de cliente nunca está em nenhum backup, em nenhum formato (limitação do Supabase Auth, hash irreversível) — restauração real sempre vai exigir resetar senha de cada cliente depois, formato-independente. **Recomendação dada (não implementada)**: manter o `.json` como está E adicionar um segundo arquivo `.sql` (dump com `INSERT`s em ordem de FK) ao mesmo backup automático diário — porque cola direto no SQL Editor do Supabase, a mesma ferramenta que o usuário já usa toda semana pras migrations, sem precisar de script de importação customizado no momento do aperto. Sugerido também guardar o arquivo num .zip protegido por senha (tem CPF/telefone/renda em texto puro). Se aprovado numa rodada futura, é um `runBackupSQL()` novo ao lado de `runBackupJSON()` em `backup-export.js`, chamado junto em `maybeRunAutoBackup()`.
- **Portabilidade de hospedagem**: auditoria de todos os `api/*.js` + `vercel.json` confirmou que o lock-in real na Vercel é **baixo** — zero imports `@vercel/*`, zero uso de Vercel KV/Blob/Edge Config, segredos são `process.env` comum, front-end sem build/bundler (já é o mais portátil possível). O único arquivo genuinamente específico da Vercel é `vercel.json` (config do cron, 3 linhas) — a lógica de negócio dos 7 endpoints não muda numa migração, só a "casca" que recebe a requisição. **Lovable explicado e descartado como opção**: é um gerador de app via IA com hospedagem própria (Lovable Cloud) — usá-lo significaria reconstruir o SIGES do zero dentro da ferramenta deles, incompatível com a exigência explícita do usuário de que só a plataforma de hospedagem mude, mantendo função/interface/identidade visual intactas. **Plataformas recomendadas, em ordem**: Netlify (Plano B — grátis permite uso comercial, funções Node quase idênticas, cron nativo, troca de menor atrito), Render (Plano C — Node.js completo, os 7 arquivos praticamente inalterados, só embrulhados num servidor Express pequeno), Cloudflare Pages+Workers (Plano D — melhor custo/performance de longo prazo, mas motor diferente da Vercel, exigiria reescrever de fato a assinatura das 7 funções — não é resposta de emergência). Nenhum arquivo de configuração de outra plataforma foi criado nesta rodada (evitar manutenção de config pra plataforma não usada) — oferecido como próximo passo opcional se o usuário quiser o "pacote de migração" pronto pro Netlify especificamente.

## Backup em .sql + pacote de migração para Netlify (2026-07-13, implementação da análise anterior)

Depois da análise de continuidade (seção acima), o usuário aprovou as duas propostas e pediu implementação direta, com o pacote de migração mantido sempre atualizado.

### Backup automático agora baixa dois arquivos

`js/screens/backup-export.js`: `runBackupSQL(silent, preloadedData)` gera um dump com `insert into ... values (...) on conflict (<PK>) do nothing;` para as mesmas 6 tabelas que já saíam no `.json` (`clients`, `loan_contracts`, `installments`, `renewal_cycles`, `payments`, `loan_requests`), na mesma ordem FK-safe que `collectAllSystemData()` já usava. `buildSqlDump(data)` monta o texto; `sqlLiteral(v)` faz a serialização por tipo (string escapada com `''`, número como está, boolean `true`/`false`, `null`→`NULL`, objeto/array→JSON stringificado). A coluna `profiles` embutida (join só pra exibição) é excluída das colunas de `clients` — não é uma coluna real da tabela.

- **`maybeRunAutoBackup()`** agora busca os dados uma vez (`collectAllSystemData()`) e reaproveita pros dois formatos (`runBackupJSON(true, data)` + `runBackupSQL(true, data)`), com um `setTimeout` de 600ms entre os dois downloads — disparar dois arquivos no mesmíssimo instante às vezes faz o navegador tratar o segundo como pop-up e bloquear silenciosamente.
- **Configurações → Backup e exportação** ganhou um segundo botão manual, "Fazer backup agora (.sql)", ao lado do já existente "(.json)".
- **O `.sql` gerado sempre abre com um comentário de aviso** explicando o pré-requisito: as contas de autenticação (`auth.users`/`profiles`) de cada cliente precisam já existir no banco de destino com os mesmos IDs antes de rodar os `INSERT`s — o Supabase Auth guarda senha como hash irreversível, então nenhum backup feito pelo navegador (sem `service_role`) consegue recriar contas sozinho. Isso não é um bug do dump, é a mesma limitação estrutural já documentada em outros lugares deste arquivo — só deixei explícito no próprio arquivo baixado, pra quem for usar num momento de aperto não ter falsa expectativa.
- **Não implementado de propósito nesta rodada**: um restaurador automático de contas (`auth.users`) a partir do backup. Recriar contas em massa é possível (mesma técnica já usada na importação de 2026-07-11, documentada acima), mas é uma ferramenta *separada*, que precisaria de `service_role` (não pode rodar no navegador) — ficou fora do escopo do que foi pedido ("o segundo download em .sql"). Se quiser esse restaurador completo no futuro, é a extensão natural: um script/endpoint novo que lê o `.sql`/`.json`, recria cada `auth.users` com senha temporária, e deixa o `handle_new_user()` cuidar do resto.

### Pacote de migração para Netlify (`netlify.toml` + `netlify/`)

Dormente enquanto o site roda na Vercel — não afeta o deploy atual em nada (a Vercel ignora `netlify.toml`, e o `vercel.json` continua sendo a configuração ativa). Existe pra reduzir o tempo de uma migração de emergência a "ativar o site no Netlify", não a "reescrever o backend".

- **`netlify/functions/_adapter.mjs`**: `adaptVercelHandler(vercelHandler)` — traduz a assinatura clássica da Vercel (`(req,res)` com `res.status(x).json(y)`) pro formato que o Netlify Functions espera (`(event) => ({statusCode,headers,body})`). Não reimplementa nenhuma regra de negócio — só a "casca".
- **`netlify/functions/<nome>.mjs`** (7 arquivos, um por endpoint: `create-user`, `delete-client`, `reset-client-password`, `update-user-email`, `wipe-all-data`, `notify-event`, `cron-daily-check`) — cada um tem 3 linhas: importa o handler ORIGINAL de `api/<nome>.js` (sem copiar/colar lógica) e reexporta via `adaptVercelHandler`. `cron-daily-check.mjs` também exporta `config = { schedule: '0 10 * * *' }` (convenção atual do Netlify Scheduled Functions, mesmo cron do `vercel.json`).
- **`netlify.toml`**: `publish = "."` (mesma raiz estática de sempre, sem build), `functions = "netlify/functions"`, e um redirect `/api/* → /.netlify/functions/:splat`. Esse redirect é o que permite que **nenhuma linha do frontend precise mudar** — confirmado por grep que todo `fetch(...)` do app usa caminho relativo (`fetch('/api/create-user', ...)`, nunca uma URL absoluta da Vercel), então o redirect resolve tudo por baixo dos panos.

**Migration a rodar manualmente no SQL Editor do Supabase:**

```sql
-- Migration 024: permite editar/reagendar uma parcela em QUALQUER status
-- (inclusive já paga/renovada, ou de contrato já finalizado/quitado) — antes
-- a RPC só atualizava linhas com status in ('pendente', 'atrasada'), então o
-- UPDATE silenciosamente não fazia nada para parcelas já pagas/renovadas,
-- mesmo que o botão de editar aparecesse no admin. A proteção contra reduzir
-- o valor abaixo do que já foi efetivamente recebido (AMOUNT_BELOW_ALREADY_PAID)
-- continua valendo sempre. Assinatura da função não muda (mesmos parâmetros),
-- então create or replace substitui a versão antiga sem precisar de drop.

create or replace function update_installment_schedule(
  p_installment_id uuid,
  p_due_date date,
  p_principal_share numeric,
  p_interest_share numeric
)
returns void
language plpgsql
security definer set search_path = public
as $$
declare
  v_installment installments%rowtype;
begin
  if not is_gerente() then raise exception 'FORBIDDEN'; end if;

  select * into v_installment from installments where id = p_installment_id;
  if v_installment.id is null then raise exception 'NOT_FOUND'; end if;

  if p_principal_share < v_installment.principal_paid_partial
    or p_interest_share < v_installment.interest_paid_partial
  then
    raise exception 'AMOUNT_BELOW_ALREADY_PAID';
  end if;

  update installments set
    due_date = p_due_date,
    principal_share = p_principal_share,
    interest_share = p_interest_share
  where id = p_installment_id;
end;
$$;
```

create or replace function update_payment_fee(
  p_payment_id uuid,
  p_has_operational_fee boolean,
  p_operational_fee_amount numeric
)
returns void
language plpgsql
security definer set search_path = public
as $$
begin
  if not is_gerente() then raise exception 'FORBIDDEN'; end if;
  if not exists (select 1 from payments where id = p_payment_id) then raise exception 'NOT_FOUND'; end if;

    has_operational_fee = p_has_operational_fee,
    operational_fee_amount = coalesce(p_operational_fee_amount, 0)
  where id = p_payment_id;
end;
$$;

## Renumeração da cadeia de renovação nas telas do cliente (2026-07-15, 2ª rodada)

Rodada anterior (migration_023, ver seção acima) corrigiu o VALOR das linhas de ciclo mas deixou a linha da PARCELA ORIGINAL sempre mostrando o valor cheio contratual, mesmo já renovada. Uma tentativa de correção nesta mesma data **reordenou fisicamente as linhas** (moveu a parcela pro final) — usuário rejeitou explicitamente ("você apenas inverteu pro final") e pediu revert imediato, que foi feito via `git revert`. A causa raiz era outra: não é a ORDEM das linhas que estava errada, é a NUMERAÇÃO/RÓTULO.

- **Modelo mental correto (confirmado explicitamente pelo usuário)**: pense na cadeia cronológica parcela → ciclo1 → ciclo2 → ... → cicloN. A ORDEM de exibição já estava certa desde sempre (parcela primeiro, ciclos depois, em `cycle_number` crescente) — **isso nunca precisou mudar**. O que muda é só o RÓTULO de cada linha, por POSIÇÃO na cadeia, não pela identidade do registro:
  - A parcela original, uma vez renovada, sempre vira rótulo fixo **"Renovação 1"** (ela é sempre a 1ª entidade da cadeia).
  - Cada ciclo intermediário (`status='renovada'`, ou seja, não é o último elo) desloca seu número **+1**: `cycle_number` 1 vira "Renovação 2", `cycle_number` 2 vira "Renovação 3", etc. — porque a parcela "roubou" o número 1.
  - O **último elo da cadeia** (o que ainda está `pendente`/`atrasada`, ou que acabou de ser `paga`/quitado) vira só **"1"** — não mais "Quitação" nem "Renovação N" — porque essa é a entidade que hoje representa "a parcela" de fato.
- **Valor de cada linha "Renovação N" (não a última) também mudou de fonte**: antes usava o `interest_only_amount` do PRÓPRIO ciclo/parcela (o juros pago quando ELE foi criado); agora usa o `interest_only_amount` do PRÓXIMO elo da cadeia (o juros pago quando ELE FOI SUPERADO) — localizado via `renewed_into_cycle_id` (parcela → ciclo) ou `previous_cycle_id` (ciclo → ciclo seguinte, precisa achar quem aponta de volta pra ele: `cyc.find(other => other.previous_cycle_id === r.id)`). Sob o modelo "juros repete" (renovação sempre cobra o mesmo valor fixo) os números numéricos costumam coincidir entre os dois campos, o que mascarava o bug — mas o campo certo importa se algum dia os valores de renovação divergirem entre si (late charge diferente, ajuste manual do gerente, etc.).
- **Verificado com simulação fiel da cascata SQL de `renew_installment`** (não só valores digitados à mão) antes de aplicar — replica exatamente `v_full_debt`/`interest_only_amount` conforme calculado no banco, incluindo o achado de que `full_debt_amount` **não cresce a cada renovação** sob "juros repete" (fica sempre travado em `principal + 1 período de juros`, já que o cliente paga o juros a cada renovação em vez de acumular). Testado com 0, 1 e 3 renovações, com e sem quitação final — todos batendo com o esperado.
- Ambas as correções replicadas identicamente em `cliente-emprestimos.js` e `cliente-indicacoes.js` (clones deliberados).
- `sw.js` em `v45`.

## Bateria de QA em empréstimos/contratos/renovações/parcelas/lucro/taxas (2026-07-15, `migration_026`)

Pedido explícito do usuário: "Faça uma bateria QA nas funções de empréstimos, contratos, renovações, parcelas, calculo de lucros e taxas." Rodada de auditoria dedicada (3 sub-análises em paralelo — contratos/parcelas; renovações/recebimentos; lucro/taxas), cada achado reverificado manualmente contra o código antes de reportar. Usuário aprovou corrigir tudo direto ("corrija tudo, faça commit e push"). 11 achados, todos corrigidos nesta rodada — 6 críticos/médios em SQL (`migration_026`), 5 médios/baixos só em frontend (sem migration).

- **QA-1 (crítico) — `renew_installment` nunca validava no servidor que o contrato era de parcela única com renovação habilitada.** Só a UI (`openReceberModal`) escondia a aba "Renovar" quando `installments_count !== 1` ou `allows_renewal === false` — uma chamada direta à RPC (fora do app) conseguia renovar qualquer contrato multi-parcela, deixando a relação entre as demais parcelas e o ciclo renovado ambígua (o próprio motivo documentado da regra "renovação só existe pra parcela única"). Corrigido buscando `installments_count`/`allows_renewal` do contrato dentro da função e rejeitando com `RENEWAL_NOT_ALLOWED` se não bater.
- **QA-2 (crítico) — contrato em `'perda'` (em cobrança) que recebia uma renovação ficava com o status congelado, nunca voltando a `'em_aberto'`.** A linha `update loan_contracts set status='em_aberto' where status in ('em_aberto','atrasado')` não incluía `'perda'` — o contrato continuava invisível pra `client_outstanding_principal()`/`client_outstanding_balance()` (que só somam `em_aberto`/`atrasado`), subestimando o limite de crédito consumido por um cliente que ainda tinha uma dívida ativa (só "renegociada" via renovação, não quitada). Corrigido incluindo `'perda'` na cláusula.
- **QA-6 (médio) — `p_late_charge_amount` nunca era validado como `>= 0`** em `renew_installment`, `receive_payment` e `receive_cycle_payment` — um valor negativo (por bug de cliente/integração futura chamando a RPC direto) reduziria o valor total cobrado sem nenhum aviso. Corrigido com `if coalesce(p_late_charge_amount,0) < 0 then raise exception 'INVALID_AMOUNT'` nas 3 funções (a UI já só envia valores não-negativos, então isso é defesa em profundidade, sem efeito prático hoje).
- **QA-7 (médio) — contrato MULTI-parcela nunca voltava de `'atrasado'` pra `'em_aberto'`.** Só `renew_installment` fazia esse retorno, e renovação é exclusiva de parcela única — um contrato de 3 parcelas que atrasava uma vez (e depois a parcela era paga/quitada) ficava com status `'atrasado'` PERMANENTE, mesmo com todas as parcelas em dia depois. Corrigido com um novo `update` em `refresh_overdue_status()` que demove `'atrasado'`→`'em_aberto'` quando não existe mais nenhuma parcela/ciclo com status `'atrasada'` naquele contrato.
- **QA-9 (médio) — `calc_installments_preview()` perdia/sobrava centavos de arredondamento.** `round(principal/count, 2)` fixo em toda parcela podia não bater com o capital total (ex: R$1.000 ÷ 3 = R$333,33 × 3 = R$999,99, faltando R$0,01). Corrigido com o método do "maior resto": a ÚLTIMA parcela absorve `total - soma_acumulada_das_anteriores`, garantindo soma exata sempre.
- **QA-5 e QA-8 (médio) — nenhuma validação impedia capital/juros negativos, nem reconciliava a soma das parcelas contra o capital do contrato.** No wizard (`gerente-contrato-novo.js`), editar o "Valor da parcela" abaixo do capital fixo da parcela gerava `interest_share` negativo (apareceria como "lucro negativo" silencioso) — corrigido travando o total mínimo no próprio capital e corrigindo o campo na tela. No backend, `create_loan_contract` (override de parcelas) e `update_installment_schedule` ganharam: (a) rejeição de `principal_share`/`interest_share` negativos, e (b) uma reconciliação `PRINCIPAL_MISMATCH` comparando `sum(installments.principal_share)` contra `loan_contracts.principal_amount` (tolerância de `0.02 × número de parcelas`) — sem isso, um typo no wizard ou na edição de uma parcela desalinhava o capital total sem aviso, distorcendo `client_outstanding_principal()` (limite de crédito).
- **QA-4 (crítico, corrigido antes dos demais) — race condition check-then-act no limite de crédito.** Nem `trg_check_credit_limit()` (criação de contrato) nem `trg_check_credit_limit_request()` (solicitação do cliente) travavam a linha do cliente antes de somar o saldo em aberto — duas criações/solicitações concorrentes (dois gerentes, ou duplo-clique) podiam, juntas, ultrapassar o limite mesmo cada uma passando na checagem isoladamente. Corrigido com `perform 1 from clients where profile_id = ... for update` logo no início dos dois triggers, mesmo padrão já usado em `receive_payment`/`renew_installment` pra parcela/ciclo.
- **QA-3 (médio, só frontend) — queries de "mês corrente" no Dashboard não tinham limite superior de data.** `paymentsMonth`/`entryFeesMonth`/`exitFeesMonth` (`gerente-dashboard.js`) usavam só `.gte(monthStart)`, sem `.lte(hoje)` — um pagamento ou contrato lançado com data futura por engano (os campos de data são editáveis manualmente) inflava o "lucro do mês"/"recebido no mês" antes mesmo do dia chegar. Corrigido adicionando `.lte(today)`/`.lte(hoje)` nas 3 queries (as queries de `prevPeriod` já faziam isso corretamente). Defesa em profundidade adicional: `max="${todayISO()}"` nos inputs de data "Data do contrato" (wizard) e "Data do recebimento" (modal de receber/renovar), pra também travar na origem.
- **QA-10 (baixo, só frontend) — os 3 relatórios (`Lucro Analítico`/`Fluxo de Caixa`/`Analítico`, `gerente-relatorios.js`) somavam `operational_fee_amount` de TODOS os contratos/pagamentos do período, sem checar o flag `has_operational_fee`.** Na prática o valor já vem zerado quando o flag está desligado (o JS de criação/edição de contrato sempre zera ao salvar), mas não valia a pena confiar cegamente nisso num relatório financeiro agregado. Corrigido filtrando `.filter(c => c.has_operational_fee)`/`.filter(p => p.has_operational_fee)` antes de somar, nos 3 lugares.
- **QA-11 (baixo, só frontend) — `periodoRange()` (`gerente-relatorios.js`) calculava o último dia do mês via `new Date(...).toISOString()`, sensível a fuso horário.** Em qualquer fuso negativo (ex: Brasil), a conversão pra UTC podia jogar a meia-noite local um dia pra trás, fazendo o relatório mensal perder o último dia do mês. Corrigido lendo o último dia via `new Date(ano, mes, 0).getDate()` (calendário local, sem `toISOString()`) e montando a data ISO manualmente — mesmo padrão de cuidado com fuso já documentado em outros lugares deste arquivo (`formatDateUTC`, `addDaysISO`).
- **Não corrigido nesta rodada (mencionado, fora de escopo)**: `addDaysISO()` (`js/utils.js`) tem a mesma fragilidade de fuso horário de raiz (`new Date(iso+'T00:00:00').toISOString()`), mas é uma função-base usada em dezenas de lugares no app — uma correção ali tem risco de regressão muito maior que o ganho, e não estava no escopo desta bateria (empréstimo/contrato/renovação/parcela/lucro/taxa). Fica registrado como candidato a uma auditoria dedicada e isolada no futuro, se o usuário quiser.
- Nenhuma alteração de assinatura de função nesta migration (todos os `create or replace` substituem a versão anterior direto, sem `drop function` necessário).
- `sw.js` em `v48`.

Também adicionados 2 eventos novos: **`logout`** (`handleSignOut()`, logado **antes** de `signOut()` — depois disso `auth.uid()` vira null no servidor e apareceria como "Anônimo") e **`emprestimo_solicitado`** (`cliente-solicitar.js`, após o insert em `loan_requests` ter sucesso). Rótulos novos em `AUDIT_ACTION_LABELS` (`gerente-auditoria.js`).
- **8. Tela Score bugada no celular — causa mais provável identificada e corrigida**: `donutChartSVG()` (`js/charts.js`) era o ÚNICO gráfico do sistema que nunca recebia `chartSize()` dos chamadores (`gerente-score.js` e a aba Analítico de `gerente-relatorios.js`) — sempre renderizava fixo em 180×180px (atributos `width`/`height` do SVG, não percentual), diferente dos outros tipos de gráfico (linha/barra/área) que já encolhem no celular por convenção documentada neste arquivo. Não foi possível reproduzir um overflow horizontal literal testando em várias larguras (320-700px) com dados sintéticos — o `flex-wrap` do container já evita estouro — mas o gráfico ficava desproporcionalmente grande perto dos cards compactos ao redor, condizente com a descrição do usuário. Corrigido: `donutChartSVG` agora detecta `window.innerWidth<=640` e usa `size=128` (com `thickness` escalado junto) em vez de 180 fixo quando o chamador não especifica `opts.size`, e o SVG ganhou `style="max-width:100%;height:auto"` como rede de segurança adicional. Efeito colateral: o donut de "Composição do período" (Relatórios → Analítico) também fica menor no celular agora, mesmo benefício.

## Análise (não implementada): fluxo de contratos em "perda" (2026-07-27)

- **Sugestões levantadas** (nenhuma implementada, aguardando decisão do usuário): (a) separar "Quitados" de "Em perda" em contadores/abas distintos, em vez de somados; (b) um card novo no Dashboard tipo "Capital em perda" (mesma metodologia de capital de `carteiraAtiva`), dando visibilidade real de exposição; (c) decidir explicitamente se `perda` deve ou não continuar bloqueando limite de crédito do cliente; (d) decidir se um contrato `perda` deve continuar aparecendo no fluxo normal de Cobrar (cobrança ativa) ou se isso é "baixa definitiva" e deveria sair de lá — e, se continuar aparecendo, pelo menos marcar visualmente essas linhas como "já em perda"; (e) um gráfico de perdas mensais (reaproveitando `areaChartSVG`/`barChartSVG` já existentes); (f) fazer `receive_payment` também reabrir `perda`→`atrasado`/`em_aberto` quando recebe um pagamento parcial, mesmo raciocínio já aplicado à renovação.

### Perda — contabilização real

- **Granularidade: por PARCELA/CICLO específico, não mais o contrato inteiro** (decisão explícita do usuário, corrigindo minha proposta inicial que era a nível de contrato). Novo valor de enum `installment_status.perda` — installments E renewal_cycles reusam o MESMO enum, então uma única `alter type` cobre as duas tabelas. Cada uma ganhou `principal_lost numeric` (capital ainda não recuperado daquela parcela/ciclo especificamente — `principal_share - principal_paid_partial` pra parcela, `loan_contracts.principal_amount` inteiro pra ciclo, já que renovação nunca abate capital) e `loss_recognized_at timestamptz` (quando foi reconhecida — nunca `due_date`/`created_at` — é o campo que define o MÊS do abate no lucro).
- **`recompute_contract_status(p_contract_id)`** (função nova): sincroniza o status do CONTRATO a partir do estado real das parcelas/ciclos — reabre (em_aberto/atrasado) se ainda há algo pendente/atrasado, ou fecha (quitado, se tudo pago; perda, se pelo menos um item foi perdido) quando não sobra nada em aberto. Substitui a lógica que antes estava duplicada/espalhada em `refresh_overdue_status`, `receive_payment` e `receive_cycle_payment` — as 3 agora só chamam essa função. Um contrato multi-parcela com só UMA parcela perdida continua `em_aberto`/`atrasado` normalmente (as outras parcelas seguem cobráveis); só fecha como `perda` quando a ÚLTIMA pendência se resolve e pelo menos uma foi perdida.
- **Perda automática** (`refresh_overdue_status`, cron diário): continua disparada pelo `loss_days_threshold` de Configurações, mas agora marca a PARCELA/CICLO específico direto (não mais o contrato). Ordem importa: a marcação de perda roda ANTES da sincronização de status do contrato, senão um contrato cuja única pendência acabou de virar perda seria promovido por engano pra `em_aberto` (não haveria mais nenhuma `atrasada` nele) em vez de corretamente fechar como `perda`.
- **Perda manual**: botão "Marcar como perda" na tabela de Parcelas do detalhe do contrato (`gerente-contratos-lista.js`), por linha (parcela normal ou ciclo de renovação atual) — funciona em qualquer parcela/ciclo `pendente`/`atrasada`, não precisa esperar o prazo automático. RPCs `mark_installment_loss`/`mark_cycle_loss`, com modal de confirmação mostrando o valor exato que será abatido do lucro do mês.
- **Reversão** (decisão explícita do usuário — "se eu quiser recuperar dívida antiga, vou no histórico e clico no botão reverter"): botão "Reverter perda" na mesma linha, quando já está `perda` — RPCs `revert_installment_loss`/`revert_cycle_loss`, volta pra `atrasada`/`pendente` conforme a data de vencimento. **Não reabre retroativamente o mês da perda já contabilizada** — se o cliente pagar depois, esse pagamento simplesmente vira lucro normal no mês em que aconteceu (mesmo padrão de "recuperação de dívida baixada" usado por bancos de verdade).
- **Some da carteira ativa e do Cobrar automaticamente** (decisão explícita do usuário — "quero que suma"): como `perda` é um status NOVO e distinto de `pendente`/`atrasada`, e Cobrar/Carteira ativa/A receber/Planejamento já filtravam estritamente `status in ('pendente','atrasada')`, a exclusão é automática — não precisou adicionar nenhum filtro novo em lugar nenhum, só criar o status novo já resolveu.

## Bugs reais de estouro horizontal no celular (2026-07-28, mesmo dia)

Usuário reportou que Cobrar/Score/Planejamento "ultrapassavam a parede" do celular. Duas causas raiz distintas, ambas confirmadas com `scrollWidth > clientWidth` no console antes de corrigir (não só inspeção visual):

- **Bug 1 — `.extrato-row .amt-wrap` (Cobrar) somava `width:100%` com `margin-left:40px`** — isso faz a caixa ficar 100% da largura do cartão **mais** 40px de margem, estourando a "parede" em exatamente essa diferença. Corrigido com uma regra genérica `.grid > * { min-width: 0; }` — conserta esse padrão em QUALQUER grid do sistema de uma vez, não só nas duas telas relatadas.
- **Refinamento extra**: a etiqueta de número do contrato no Cobrar virou uma pílula pequena de verdade (`.extrato-row .tag`, fundo `--bg`, cantos bem arredondados) em vez de texto corrido com "·" — mais fiel ao mockup aprovado, que usava exatamente esse selo.

Corrigido comparando por ÍNDICE do ponto (atributo `data-idx` no elemento), não por igualdade de coordenada. Fica registrado aqui porque é o tipo de bug fácil de reintroduzir em qualquer gráfico novo com hover feito à mão (fora do `initAreaCharts` já testado) — sempre comparar por índice, nunca por igualdade de float/coordenada arredondada.

## Bug real corrigido: "Promise rejeitada sem tratamento: supa.rpc(...).catch is not a function" toda vez na Auditoria (2026-08-02)

Usuário reportou ver esse erro repetidamente em Auditoria. Causa: `js/auth.js`, dentro de `onAuthenticated()` (item 3 da "Rodada de 9 melhorias", 2026-07-27) — `supa.rpc('recalculate_all_scores').catch(() => {...})`. O objeto devolvido por `supa.rpc(...)` (e por `supa.from(...)`) é um builder "thenable" do supabase-js: implementa `.then()` (por isso `await` funciona nele), mas **não é uma `Promise` de verdade** — não implementa `.catch()`/`.finally()`. Encadear `.catch()` direto nele lança `TypeError: ... .catch is not a function` na hora (síncrono), e como essa chamada vive dentro de `onAuthenticated()` (uma função `async` que ninguém aguarda/trata), o erro virava uma REJEIÇÃO DE PROMISE NÃO TRATADA a cada login de gerente — capturada automaticamente pelo listener global `unhandledrejection` (`main.js`) e logada como `erro_sistema`.

- **Corrigido** trocando `.catch(fn)` por `.then(() => {}, fn)` — a forma de 2 argumentos de `.then()` (`onFulfilled, onRejected`) faz parte do próprio contrato "thenable" que esse objeto realmente implementa, diferente de `.catch()` (que é açúcar sintático de `Promise` de verdade).
- **Regra pra não repetir**: qualquer chamada fire-and-forget (sem `await`) a `supa.rpc(...)`/`supa.from(...)` que precise tratar erro sem travar o fluxo deve usar `.then(onFulfilled, onRejected)`, nunca `.catch(...)` encadeado direto no builder. Se preferir `await`, sempre dentro de um `try/catch` (como os outros 3 efeitos colaterais de `onAuthenticated()` já fazem) — nunca confiar que o builder do supabase-js aceita `.catch()` como uma Promise nativa aceitaria.
- Confirmado por grep que essa era a ÚNICA ocorrência de `.catch(` encadeado em `supa.rpc`/`supa.from` no projeto inteiro — não há outro lugar com o mesmo bug.
- `sw.js` em `v60`.

## Bug real corrigido: gráficos de barra/linha colados na borda esquerda do card (2026-08-03)

Usuário reportou com print real: o gráfico "Lucro por período" (Relatórios → Lucro Analítico) aparecia visivelmente deslocado pro canto esquerdo do card, com um vão vazio grande à direita, sempre que a série tinha poucos pontos (card mais largo que o `viewBox` pensado pro desktop).

- **Causa raiz**: `barChartSVG`/`lineChartSVG`/`areaChartSVG` (`js/charts.js`) usam `width="100%"` combinado com `style="max-width:${w}px"` — quando o card é mais largo que esse `max-width` (comum em Relatórios, cujos cards ocupam a largura cheia da tela), o SVG renderiza na largura travada (ex: 600px) mas gruda na borda ESQUERDA por padrão, já que `<svg>` sem `display:block;margin:auto` não centraliza sozinho quando sobra espaço no pai.
- **Corrigido** adicionando `display:block;margin:0 auto` no `style` do `<svg>` das 3 funções — centraliza o desenho sempre que ele é mais estreito que o card, sem efeito nenhum quando o SVG já preenche 100% do espaço disponível (que continua funcionando exatamente como antes). `donutChartSVG` não precisou de ajuste — já vive numa linha flex ao lado da legenda, nunca sozinho ocupando a largura cheia do card.
- Testado renderizando "Lucro Analítico" e "Fluxo de Caixa" com dados sintéticos (poucos meses, card largo) — confirmado por `getBoundingClientRect()` que o vão esquerdo e direito do SVG dentro do card ficam iguais nos dois casos (bar chart e os 2 line charts lado a lado).
- **Se um gráfico novo usar esse mesmo padrão de `viewBox` + `max-width` no futuro, replique `display:block;margin:0 auto` junto** — é um comentário deixado no topo de `charts.js`, perto de `chartSize()`, exatamente pra não se perder de novo.

### Fase 1c implementada — isolamento de ESCRITA (2026-08-09)

A fase de maior risco técnico do projeto inteiro. Catalogadas TODAS as ~40 funções `security definer` do schema (via grep exaustivo), classificadas em: helpers já corretos, triggers de negócio sem dado de cliente (sem risco), funções de leitura (já fechadas na Fase 1b), e **23 funções de escrita** que precisavam de correção — todas corrigidas em `supabase/migration_034.sql`.

**Por que RLS (Fases 1a/1b) não bastava aqui**: toda função `security definer` roda como DONA da tabela, então BYPASSA RLS completamente. As políticas corrigidas nas fases anteriores não protegem nada dentro dessas funções — cada uma precisa validar tenant por conta própria.

**Achado mais grave de toda a auditoria**: `wipe_all_business_data()` (o botão "Apagar tudo" de Configurações → Zona de risco) fazia `delete from X where true` em toda tabela de negócio — apagava a PLATAFORMA INTEIRA, não só o tenant de quem clicou. Um admin primário de qualquer empresa cliente do SaaS conseguiria, com ou sem querer, destruir os dados de todas as outras empresas de uma vez. Corrigido: cada delete agora é `where tenant_id = current_tenant_id()`.

**Padrão de correção aplicado nas 23 funções**:
- Toda leitura de linha POR ID (`select ... where id = p_X`) ganhou `and tenant_id = current_tenant_id()`, com `NOT_FOUND` genérico quando não bate (nunca revela "existe mas é de outro tenant").
- Todo `insert` em tabela com `tenant_id` passou a setar o valor explicitamente (`v_tenant_id := current_tenant_id()` no início da função), em vez de depender do `default_tenant_id()` provisório da Fase 0.
- `receive_payment`/`receive_cycle_payment`/`renew_installment` (as 3 funções que gravam dinheiro de verdade) eram as mais graves — sem a correção, um gerente de outra empresa podia registrar pagamento/renovação contra parcela de QUALQUER tenant.
- `recalculate_all_scores()` iterava `select profile_id from clients` sem filtro — recalculava score de TODOS os clientes da plataforma a cada clique em "Recalcular todos". Corrigido pra `where tenant_id = current_tenant_id()`.
- `log_audit_event()`: retenção de 500 eventos (`migration_029`) agora é PODADA POR TENANT, não pela tabela inteira — senão um tenant ativo empurraria pra fora o histórico de outro, inclusive o do dono da plataforma.
- `recompute_contract_status()` ganhou checagem `is_gerente() or service_role` (não tinha NENHUMA antes — não vazava/corrompia dado, mas não devia ser chamável por conta de cliente).
- `refresh_overdue_status()` (cron) e a chamada de `recalculate_client_score()`/`recompute_contract_status()` feita a partir dele foram deliberadamente MANTIDAS sem escopo de tenant — o cron roda com `service_role`, sem `auth.uid()`, e precisa processar TODOS os tenants por design. `recalculate_client_score()` ganhou lógica condicional: escopa por tenant quando chamada por um gerente de verdade, mas não quando vem do cron.

**Achados extras fora do SQL (arquivos `api/*.js`, também corrigidos)** — a mesma classe de bug (escrita via `service_role`, bypassa RLS, sem checar tenant), encontrados ao seguir o rastro de `wipe_all_business_data()`:
- **`api/wipe-all-data.js`**: buscava `role=eq.cliente` sem filtro de tenant pra depois apagar as contas `auth.users` — mesmo com o SQL corrigido, esse passo sozinho continuaria destruindo as CONTAS DE LOGIN de clientes de outras empresas. Corrigido com `&tenant_id=eq.${caller.tenant_id}`.
- **`api/create-user.js`**: não passava `tenant_id` no `user_metadata` do novo usuário — TODO cadastro criado por QUALQUER gerente caía no Tenant #1 (fallback do `default_tenant_id()`), não importa de qual empresa o gerente really era. Corrigido passando `tenant_id: caller.tenant_id`.
- **`api/delete-client.js`**, **`api/reset-client-password.js`**, **`api/update-user-email.js`**: nenhum verificava se o alvo (`target`) pertencia ao mesmo tenant do chamador — um gerente conseguia excluir conta, redefinir senha ou trocar e-mail de QUALQUER usuário (cliente ou até gerente) de QUALQUER outra empresa da plataforma. Sequestro de conta entre empresas. Corrigido com `target.tenant_id !== caller.tenant_id` → 404 genérico nos 3.
- **`api/notify-event.js`**: `solicitacao_criada` notificava TODO gerente ativo da plataforma (sem filtro de tenant); outros eventos não verificavam se o `client_id` alvo pertencia ao tenant do gerente. Ambos corrigidos.
- **`api/_lib/supabaseAdmin.js`**: `getCallerProfile()`/`getTargetProfile()` passaram a selecionar `tenant_id` também (pré-requisito pras correções acima).
- Nenhum desses arquivos teve a ASSINATURA `(req, res)` alterada nem foi criado/removido/renomeado — só lógica interna — então, pela regra já registrada neste documento, **não precisou tocar em `netlify/`**.

**Zero mudança de comportamento hoje**, mesmo raciocínio de todas as fases anteriores — só existe 1 tenant.

```sql
alter table profiles add column platform_owner boolean not null default false;

update profiles set platform_owner = true
  where id = (select owner_profile_id from tenants order by created_at asc limit 1);

create or replace function prevent_profile_privilege_escalation()
returns trigger
language plpgsql
security definer set search_path = public
as $$
begin
  if (new.role is distinct from old.role
      or new.is_primary_admin is distinct from old.is_primary_admin
      or new.active is distinct from old.active)
     and not is_primary_admin()
     and coalesce(auth.role(), '') <> 'service_role' then
    raise exception 'FORBIDDEN: só o administrador primário pode alterar papel/privilégio/status de uma conta';
  end if;

  if new.platform_owner is distinct from old.platform_owner
     and coalesce(auth.role(), '') <> 'service_role' then
    raise exception 'FORBIDDEN: platform_owner só pode ser alterado internamente';
  end if;

  return new;
end;
$$;

drop trigger if exists trg_prevent_profile_privilege_escalation on profiles;
create trigger trg_prevent_profile_privilege_escalation
  before update of role, is_primary_admin, active, platform_owner on profiles
  for each row execute function prevent_profile_privilege_escalation();
```

### Fase 5 — planos configuráveis (Basic/Essential/Premium, sem cobrança) (2026-08-10)

Implementada, testada no preview (CRUD de planos, atribuição por empresa, gates de UI, desktop e mobile), **ainda não confirmada em produção** — falta o usuário rodar `migration_039.sql`.

- **Fecha 2 requisitos originais do pivô SaaS que ainda não tinham sido implementados** (achado ao planejar esta fase, não pedido de novo pelo usuário): "Planejamento é só meu" e "Configurações não terá zona de risco" pra empresa cliente da plataforma — as duas frases já estavam na mensagem original que abriu a transformação em SaaS, mas só a Auditoria tinha recebido esse tratamento até agora (Fase 3).

Chaves de v1 (definidas em `PLAN_LIMIT_FIELDS`, extensível sem migration — só código): `max_gerentes`/`max_clientes` (inteiro, vazio = ilimitado) e `allow_extrato_pdf`/`allow_promissoria_pdf`/`allow_backup_export` (boolean, ausente = liberado). `tenants.plan_id` é nullable — **`null` = sem plano = sem limite nenhum**, o comportamento de toda empresa hoje (inclusive a sua), até o Administrador Master atribuir um plano manualmente pela tela **Empresas** (novo seletor no modal de editar, `assign_tenant_plan()`).
- **Enforcement de `max_gerentes`/`max_clientes`**: dois caminhos.

Levanta `CLIENT_LIMIT_EXCEEDED`, traduzido em `traduzErroAuth()` (`js/auth.js`) pra uma mensagem amigável. **Cuidado se mexer nesse trigger no futuro**: todo usuário (inclusive um futuro gerente) nasce `role='cliente'` aqui antes de uma eventual promoção — o check teria que continuar isolado ao branch "sem tenant_id direto", senão bloquearia criação de gerente por engano quando o tenant já estiver no limite de CLIENTES.
- **Enforcement de `allow_extrato_pdf`/`allow_promissoria_pdf`/`allow_backup_export`**: só client-side (UI) — nenhuma dessas 3 features tem endpoint de servidor hoje (PDF é 100% `jsPDF` no navegador, backup é download direto), então criar um servidor só pra gatear seria desproporcional pra esta fase. - **`list_tenants_with_stats()` mudou de `RETURNS TABLE` DUAS vezes agora** (Fase 4 acrescentou `invite_token`, esta fase acrescenta `plan_id`/`plan_name`) — cada mudança de retorno precisou de `drop function` antes do `create or replace` (mesma trava do Postgres já documentada aqui pra mudança de parâmetro, também vale pra tipo de retorno).
- **Sem cobrança/pagamento nenhum nesta fase** — `price_monthly` é só informativo (nunca cobrado automaticamente). Cupons e processamento de pagamento de verdade (Stripe ou similar) continuam fora de escopo, não pedidos ainda.

### Fase final — Backup Geral do Administrador Master (2026-08-10)

Implementada e testada no preview (desktop e mobile, conteúdo do .json/.sql inspecionado diretamente) — **sem migration nenhuma**, essa fase não precisou de nenhuma mudança de schema/RLS/RPC (ver "por que zero SQL" abaixo). Fecha o último item da lista original do pivô SaaS.

- **Nova tela "Plataforma SaaS → Backup Geral"** (`js/screens/plataforma-backup.js`, rota `plataforma/backup`) — 2 botões, `.json` e `.sql`, mesmo padrão visual/técnico do backup de sempre (`backup-export.js`: `downloadBlob()`, `sqlLiteral()`, `buildSqlDump()`-like), mas cobrindo só 3 tabelas: `tenants`, `plans`, `audit_log` (todas as empresas — o único lugar do sistema com essa visão cross-tenant, mesma exclusividade de sempre da Auditoria).
- **Decisão de escopo deliberada, não limitação técnica**: este backup **nunca** inclui clientes/contratos/parcelas/pagamentos de NENHUMA empresa (nem a sua). Bulk-exportar dados de clientes de OUTRAS empresas pro seu próprio computador, só porque você é o dono da infraestrutura, seria uma invasão de privacidade desproporcional ao papel de Administrador Master — nenhum provedor de SaaS sério faz isso rotineiramente com dado de cliente de terceiros. O backup do SEU PRÓPRIO negócio (Tenant #1) continua exatamente onde sempre esteve — Configurações → Backup e exportação — sem nenhuma mudança; a tela nova só tem uma nota apontando pra lá, pra não confundir "cadê meus clientes nesse backup".
- **Por que zero SQL nesta fase**: as 3 tabelas cobertas já tinham RLS `is_platform_owner()`-only de fases anteriores (`tenants_select`, `plans_select_platform_owner`, `audit_log_select_platform_owner`) — o Administrador Master já enxerga TODAS as linhas de TODOS os tenants nessas 3 tabelas via `supa.from(...).select(...)` direto, sem precisar de nenhuma RPC nova. A tela só lê o que a RLS já deixava ler.
- **Sem backup automático nesta tela** (diferente do backup do tenant, que tem toggle de frequência) — dados administrativos (empresas/planos/auditoria) mudam bem menos que dado financeiro do dia a dia; um botão manual "Baixar agora" foi considerado suficiente pra v1, evitando complexidade desproporcional ao volume de mudança dos dados.
- **Zero mudança de comportamento pra qualquer perfil que não seja o Administrador Master** — confirmado no preview: item de menu não aparece, rota redireciona se acessada via hash direto (mesmo guard `role: 'plataforma'` já usado por Início/Empresas/Planos).
- `sw.js` em `v67` (novo arquivo `js/screens/plataforma-backup.js` adicionado ao cache).

**Com isso, as 6 fases da transformação SIGES → Plataforma SaaS (Fase 0 a esta) estão completas.** Únicos itens conscientemente fora de escopo, nunca pedidos como fase própria: cobrança/pagamento real (Stripe ou similar) e cupons — `plans.price_monthly` continua só informativo, sem nenhuma cobrança automática.

## Fechamento das lacunas entre o mockup e a implementação (2026-08-10, achados testando uma 2ª empresa em produção)

Depois de completar as 6 fases da transformação em SaaS, o usuário pediu um teste de ponta a ponta criando uma segunda empresa de verdade em produção (não só mockado no preview) — o primeiro teste real desde a Fase 0. Esse teste ao vivo achou 2 bugs reais que nenhum teste mockado anterior conseguiria pegar (porque dependiam de dados reais de uma SEGUNDA empresa existindo), mais o recurso de excluir empresa que ele pediu na sequência.

- **Bug real corrigido (`migration_040.sql`): solicitação de empréstimo de cliente de empresa assinante caía na caixa "Solicitações" do Administrador Master.** Causa: `cliente-solicitar.js` nunca envia `tenant_id` no insert em `loan_requests` — a coluna sempre caía no DEFAULT (`default_tenant_id()`, que resolve pro Tenant #1, o seu próprio negócio). Reproduzido e confirmado ao vivo: cliente da "Empresa Teste QA" solicitava empréstimo, caía na sua caixa. Corrigido forçando `tenant_id = current_tenant_id()` dentro do trigger `trg_check_credit_limit_request()` (já existia, `before insert on loan_requests`) — nunca confiando em nada que o cliente mandou (ou deixou de mandar). Migration inclui também um `update` de reparo pra qualquer `loan_requests` já existente que tenha caído no tenant errado (comparando contra `profiles.tenant_id` do cliente dono da solicitação).
- **Bug real corrigido (`migration_041.sql`): tela Configurações de QUALQUER empresa assinante nova ficava permanentemente quebrada** ("Não foi possível carregar as configurações agora"). Causa: `system_settings` nunca teve a chave primária corrigida quando ganhou `tenant_id` (Fase 0) — continuava sendo `id boolean primary key default true check(id)`, um resquício do tempo de "singleton global" antes do pivô SaaS. Isso limitava a tabela a UMA linha em todo o banco (violação de unicidade em `id` bloqueava qualquer segunda linha), então nenhuma empresa criada depois da Fase 0 conseguia ter a própria linha de configurações — confirmado ao vivo com a Admin Teste QA. Corrigido: `tenant_id` vira a PK de verdade (`alter table ... drop constraint system_settings_pkey; add primary key (tenant_id)`), a migration cria a linha que faltava pras empresas já existentes, e um novo trigger `after_tenant_created` garante que toda empresa NOVA (qualquer caminho de criação futuro, não só `api/create-tenant.js`) já nasce com a própria linha de configurações (usando o nome da empresa como `company_name` inicial). **Esse padrão vale a pena lembrar**: qualquer tabela "singleton" antiga (`id boolean`/fixo) que ganhar `tenant_id` no futuro precisa ter a PK revisada — adicionar a coluna sozinha não basta.
- **Novo recurso: excluir empresa** (Administrador Master, tela Empresas) — irreversível, com 3 travas: nunca a própria empresa de quem chama, só funciona com a empresa **já suspensa** (força passar por "desativar" antes, evita 1-clique numa empresa ainda ativa), e exige digitar o nome exato da empresa pra confirmar (mesmo princípio da Zona de risco, que exige digitar "APAGAR TUDO"). `prepare_tenant_deletion(p_tenant_id)` (RPC) apaga todo dado de negócio do tenant (mesmas tabelas de `wipe_all_business_data`, mas escopado a `p_tenant_id`, e cobrindo TAMBÉM `planning_debts`/`system_settings`, que aquela função não tocava por ser "apagar meus dados", não "apagar a empresa inteira") e devolve os `profile_id` (gerentes + clientes) restantes; `api/delete-tenant.js` (novo, service_role) apaga cada conta via Admin API (cascateia `profiles`/`clients` automaticamente) e só then apaga a linha de `tenants` em si — profiles ainda referenciando o tenant bloqueariam isso antes. Netlify wrapper criado no mesmo commit.
- Ambos os bugs só existiam porque, até este teste, NENHUMA sessão anterior tinha testado o fluxo com uma segunda empresa de verdade em produção — todo teste anterior (Fases 2-5) foi feito com dados mockados no preview local, que nunca exercitam RLS/triggers/constraints reais do Postgres. Fica registrado como lição: testes mockados provam que a UI/lógica JS está correta, mas não substituem pelo menos um teste ao vivo com uma segunda empresa real depois de qualquer rodada grande de mudança de schema multi-tenant.
- `sw.js` em `v68`.

## Painel executivo da Plataforma SaaS (2026-08-10, `migration_042.sql`)

"Plataforma SaaS → Início" deixou de ser um stub e virou o painel executivo pedido pelo usuário depois do teste de ponta a ponta com uma 2ª empresa — assinantes, receita, uso agregado da plataforma inteira, saúde operacional e rankings. Implementadas TODAS as sugestões levantadas (usuário: "Implemente todas"), sem cortar nenhuma.

- **`get_platform_dashboard_stats()`** (RPC nova, `is_platform_owner()`-only) devolve um jsonb único com tudo que a tela precisa — um round-trip só, em vez de uma query por métrica. Três blocos: `summary` (números agregados), `by_plan` (contagem + MRR por plano), `tenants` (detalhe por empresa, usado no frontend pra derivar rankings/alertas sem round-trip extra).
- **MRR/ARR/ticket médio**: soma de `plans.price_monthly` das empresas ATIVAS com plano atribuído — sem cobrança automática nenhuma, é só informativo (mesma ressalva já documentada na Fase 5).
- **`tenants.suspended_at`** (novo) — marcado sempre que `update_tenant()` suspende a empresa, **nunca limpo ao reativar** (decisão deliberada: fica registrando "última vez suspensa", não "está suspensa agora" — isso já é o campo `active`). Usado só pra "tempo médio de vida até suspensão" (`avg(suspended_at - created_at)` das empresas já suspensas alguma vez).
- **Churn** = suspensões + exclusões no mês / total de empresas. Exclusões (empresas apagadas de vez, sem registro na tabela `tenants`) são contadas via `audit_log` (ação `empresa_excluida`, já logada desde a Fase de excluir empresa) — é o único jeito de saber que uma empresa existiu e foi removida, já que a exclusão é um hard-delete de verdade.
- **`total_capital_active`** (capital emprestado somado de TODAS as empresas) usa `SUM(loan_contracts.principal_amount)` dos contratos em aberto/atrasado — uma aproximação deliberadamente mais simples que a metodologia "carteira ativa" de cada Dashboard individual (que desconta capital já pago via installments). Para uma visão executiva agregada de "o tamanho da plataforma", essa simplificação é aceitável; não é uma reconciliação contábil exata.
- **"Sem atividade recente"** (saúde operacional) = 0 contratos ativos E (nenhum evento `login_sucesso` no `audit_log` daquela empresa OU o último login foi há mais de 30 dias). Como `audit_log` é podado a 500 eventos por tenant (Fase 1c), uma empresa muito antiga com muito volume de eventos recentes poderia ter o login mais antigo "rolado pra fora" do histórico — limitação aceita, não um bug.
- **"Perto do limite do plano"** = `gerente_count/max_gerentes >= 90%` OU `cliente_count/max_clientes >= 90%`, só pra empresas com plano que tenha esses limites numéricos definidos (ausência de chave = sem limite = nunca aparece aqui, mesmo tratamento de `planAllows()`/enforcement da Fase 5).
- **Rankings** (top por clientes, top por capital, mais novas) são derivados client-side a partir do MESMO array `tenants` já trazido pelo `summary` — não são 3 queries a mais.
- Gráficos reaproveitam `donutChartSVG`/`donutLegendHtml` (distribuição por plano) e `barChartSVG` (receita por plano, com suporte a valor negativo já herdado — não usado aqui mas não atrapalha) — nenhum componente novo de visualização, só reuso.

## Bug real corrigido: scroll horizontal fantasma no modo "Plataforma SaaS" no celular (2026-08-10)

Achado testando o painel executivo (seção acima) ao vivo num viewport de 375px — `document.documentElement.scrollWidth` (388px) excedia `clientWidth` (375px), mas só no modo Plataforma SaaS (modo Empréstimos, mesma sessão, batia exatamente 375=375).

- **Investigação não encontrou nenhum elemento visualmente estourando a tela** — nem por `getBoundingClientRect().right`, nem por pseudo-elementos com `content`, nem isolando `<main>`/sidebar/tabbar um a um. Uma medição pontual chegou a flagrar a `.card.stat-card` de "Tempo médio até suspensão" (dentro da `kpi-grid-4` de 4 KPIs, 2 colunas no celular) com um overflow interno transiente — mas remedido logo depois, o mesmo elemento já batia exatamente com sua coluna (label wrapped em 2 linhas, sem overflow). Conclusão: é arredondamento sub-pixel acumulado em colunas fracionárias de CSS Grid (`grid-template-columns` computando `166.5px 166.5px`, por exemplo) — o navegador soma alguns pixels a mais no `scrollWidth` mesmo sem nenhum elemento realmente ultrapassar a borda visível, especialmente em telas com grid bem aninhado (KPIs → cards → labels) como este painel novo. O modo Empréstimos não tem esse mesmo grau de aninhamento nas telas mais comuns, por isso não reproduzia.
- **Corrigido com uma rede de segurança global**: `overflow-x: hidden` em `html, body` (`style.css`, junto do reset de margin/padding de sempre) — trava a capacidade de rolar/arrastar a página na horizontal, independente de qualquer arredondamento futuro. Confirmado seguro: nenhuma tela do sistema depende de scroll horizontal no nível do `body` (tabelas `.table-scroll` no desktop nunca tiveram `overflow-x:auto` própria — não existe esse padrão no CSS —, e no celular viram cards empilhados, sem coluna nenhuma pra rolar). Um scroll horizontal interno legítimo dentro de algum componente (se um dia existir) continuaria funcionando normal — `overflow-x:hidden` no body só afeta o que extrapola a própria caixa do body, nunca o scroll interno de um filho.
- Testado ao vivo (produção): com a regra aplicada via `javascript_exec`, `document.documentElement.scrollWidth` voltou a bater exatamente com `clientWidth` (375=375) no modo Plataforma SaaS, sem nenhuma mudança visual (nenhum elemento estava realmente visível além da borda antes da correção).
- `sw.js` em `v70`.

## Limitações conhecidas (v1, ver README para detalhes)

- **E-mail para clientes está desativado de fato (decisão consciente, 2026-07-07).** O usuário não tem domínio próprio registrado (só tentou cadastrar `siges.com.br` no Resend sem possuir o domínio de verdade — verificação trava em "Not Started" porque não há onde adicionar os registros DNS). Decisão: não registrar domínio por enquanto; os canais reais de notificação do cliente são o **sino in-app** (Supabase Realtime) e o **Web Push** (ambos gratuitos, já funcionando). `RESEND_FROM_EMAIL` continua sem valor em produção, então todo envio cai no remetente sandbox `onboarding@resend.dev`, que só entrega para o e-mail da própria conta Resend — **isso é esperado, não é bug**. Email e push são canais independentes em `dispatchToRecipient` (`api/notify-event.js`), então a falha de e-mail não afeta a entrega do push. Se o usuário decidir registrar um domínio no futuro, o caminho é: Resend → Domains → verificar DNS → configurar `RESEND_FROM_EMAIL` no Vercel — nenhuma mudança de código é necessária.
- WhatsApp é só via link `wa.me` (zero custo, sem API paga) — não há envio automático de WhatsApp pelo servidor.
- Sem paginação em nenhuma listagem (`gerente-clientes.js`, `gerente-contratos-lista.js` etc.) — inofensivo no volume atual, mas é o primeiro ponto a atacar se o negócio crescer muito.
- Sem testes automatizados — valide sempre manualmente no preview, incluindo viewport mobile.

## Onde procurar o quê

- `supabase/schema.sql` — schema completo "fresh install", toda regra de negócio sensível vive aqui como função SQL (`security definer`), nunca só em JS.
- `js/screens/*.js` — uma tela por arquivo, registradas via `registerRoute(...)` no fim de cada arquivo. `js/main.js` é sempre o último `<script>` carregado.
- `js/charts.js` — gráficos SVG inline reutilizáveis (`barChartSVG`, `lineChartSVG`, `donutChartSVG` + `donutLegendHtml`).
- `api/*.js` — únicas rotas que usam a `service_role` key ou outras chaves secretas (Resend, VAPID, CRON_SECRET).
